# Availability read model (граница домена)

По ADR **маркетплейса** (`docs/adr/marketplace-offerings-search.md`): **слоты и занятость календаря** не являются частью агрегата `OrganizationOffering`.

- Read-модель доступности строится поверх **employment + расписание специалиста** (отдельный bounded context / фоновые задачи).
- Ответы листинга и SQL directory **не должны** смешиваться с тяжёлой логикой «свободных слотов всей сети» в одном hot path.
- Консистентность с бронированием: **eventually** (§3.0.6); критичная консистентность — в OLTP при создании записи.

## Growth constraint (буферы, выезд, кабины)

Текущий MVP опирается на **пересечение активных броней** и политику сетки слотов — этого недостаточно при:

- буферах между клиентами;
- **выездном** сервисе (travel time);
- **нескольких кабинах** и мастерах в одном салоне;
- сценариях «несколько исполнителей на одну запись».

Тогда availability становится **ограничителем роста**, а не «отдельной фичей календаря»: планировать отдельный bounded context **до** появления этих сценариев в roadmap.
